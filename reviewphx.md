## Pass 1: Detailed review findings

### 1. Rendering pipeline (Draw.cpp, RenderState.cpp, RenderTarget.cpp, RenderJobQueue.cpp)

**Draw.cpp (790 lines) — Deferred flat batch + widget batch**
- ✅ Well-structured: VBO-based (no deprecated immediate mode), flat batch for color-state draws, widget batch for SDF rects.
- ✅ Overflow handling: `Draw_Enqueue` commits and continues when `s_count >= DRAW_MAX_VERTS`. `Imm_Draw` chunks into DRAW_MAX_VERTS slices.
- ✅ `Draw_FlushPending()` hooked at RenderState/RenderTarget/Shader_Start/ShaderVar/Window boundaries.
- ⚠️ `Draw_Push` silently drops vertices when `s_count >= DRAW_MAX_VERTS` (returns without growing). This is a safety valve — the batch commits before overflow in Draw_Enqueue, but direct Draw_Push callers could lose vertices. Low risk (batch commits first).
- ✅ Widget batch (roadmap #15) merges consecutive same-key rects into one draw. Good.

**RenderState.cpp (110 lines)** — Clean. Push/pop for blend, depth, cull, etc. Each calls Draw_FlushPending.

**RenderTarget.cpp (181 lines)** — Clean. Push/pop with FBO binding. Calls Draw_FlushPending.

**RenderJobQueue.cpp (134 lines)** — Thread pool for rigid body matrix extraction.
- ✅ Proper mutex/cond usage, generation-based wakeup (avoids missed-wakeup deadlock).
- ✅ Workers process disjoint slices, no GL/Lua/allocator access.
- ✅ Cleanup properly signals stop and joins threads.
- ⚠️ Cap of 8 workers (hardcoded). Fine for current hardware.

### 2. Shader system (Shader.cpp, ShaderState.cpp, ShaderVar.cpp)

**Shader.cpp (530 lines)** — Shader loading, compilation, autovar management.
- ✅ Graceful failure: falls back to last-good shader on compile/link failure (AGENTS.md item 4).
- ✅ `#autovar` lines are stripped during preprocess and registered for stack upload.
- ⚠️ Autovar upload is eager (at Shader_Start), not per-draw. This is the "autovar trap" documented in AGENTS.md.
- ⚠️ `#autovar` lines must be stripped; the shader must still declare a real `uniform`. Documented.

**ShaderState.cpp (223 lines)** — Shader state management. Clean.

**ShaderVar.cpp** — Shader variable stack. Clean.

### 3. Font system (Font.cpp) — RECENTLY FIXED

**Font.cpp (456 lines) — glyph atlas (shelf-packed, per-font)**

### Phase 14 — Gen pipeline (SDF) — DISCUSSION

The Gen pipeline (SDF.cpp, Mesh_FromSDF.cpp, etc.) uses many intermediate buffers for procedural mesh/planet generation. This is the main memory hotspot.

**What it does:**
- Generates SDF (signed distance field) volumes on the CPU
- Converts SDF to meshes via marching cubes
- Generates planet surfaces, asteroid meshes, nebula volumes

**Memory implications:**
- Each SDF volume is a 3D grid of floats (e.g., 64³ = 262K floats = 1MB per volume)
- Multiple intermediate buffers exist during generation (SDF → mesh → LOD)
- Planet generation creates several volumes (surface, atmosphere, clouds)
- Peak memory during planet gen could be 10-50MB depending on resolution

**Options:**
1. **Leave as-is** — generation is one-time per sector/planet, not per-frame. Memory is freed after gen. Low priority.
2. **Reduce SDF resolution** — lower gen quality but less memory. Configurable via gen parameters.
3. **Stream generation** — generate chunks instead of full volumes. Major refactor.
4. **Pool/reuse buffers** — reduce allocations. Medium effort.

**Recommendation:** Option 1 (leave as-is). The gen pipeline runs once per sector entry (not per-frame), and memory is freed after generation. The peak memory (~10-50MB) is acceptable for a desktop game. If memory becomes an issue on low-end hardware, Option 2 (reduce resolution) is the simplest fix.
